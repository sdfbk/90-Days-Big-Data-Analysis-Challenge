PySpark is the Python API for Apache Spark, while Spark SQL is a Spark module for structured data processing using SQL queries or the DataFrame

Key Difference:
Language Interface: PySpark uses Python code and method chaining (e.g., df.filter()), whereas Spark SQL uses standard ANSI SQL queries (e.g., spark.sql("SELECT * FROM table")).
PySpark fits best for complex programmatic workflows, machine learning pipelines, and custom Python functions (UDFs). Spark SQL fits best for data warehousing, reporting, and users with a pure SQL background. 
PySpark requires inter-process communication between Python worker processes and the Java Virtual Machine (JVM) via Py4J for certain operations, whereas native Spark SQL runs entirely within the JVM without cross-language bridge overhead. 
PySpark offers deep control over custom logic and data flows, while Spark SQL offers a cleaner, more declarative syntax for relational operations.

E) Partitioning and bucketing
Partitioning and bucketing are data organization techniques used in big data frameworks (like Apache Spark, Hive, and Databricks) to optimize query performance and avoid full table scans.  
Partitioning 
Partitioning physically divides a large dataset into separate folders or directories on disk based on the distinct values of a specific column. 

• Cardinality: Best used for low-cardinality columns (columns with a small number of unique values, like  or ). 
• How it works: If you partition by , Spark creates separate subdirectories like  and . 
• Query optimization: When a query includes a filter like , the engine uses partition pruning to skip scanning all other directories entirely. 
• Pitfall: Partitioning on high-cardinality columns (like user_id or timestamp) creates thousands of tiny folders and files, which degrades performance (known as the "small file problem").  

Bucketing (Clustering) 
Bucketing organizes data within a partition (or an unpartitioned table) into a fixed, predefined number of files by applying a hash function to the values of a specific column. 

• Cardinality: Best used for high-cardinality columns (columns with many unique values, like  or ). 
• How it works: The system applies a hash function (e.g., hash(column) % num_buckets) to group rows into a set number of data files. 
• Query optimization: Bucketing co-locates related data together, which eliminates data shuffling during expensive join and aggregation operations on the bucketed columns. Read more about organizing data layouts and co-location in Spark Partitioning and Bucketing.  

Key Differences at a Glance 

• Structure: Partitioning creates physical directories; bucketing creates a fixed number of hashed files within those directories or tables. 
• Key Definition: Partition values are dynamic and driven by data; bucket count is static and must be defined explicitly by the user during creation. 
• Primary Benefit: Partitioning speeds up filtering ( clauses) via directory skipping; bucketing speeds up joins and group-bys by removing shuffles.  

Combining Both 
For large enterprise datasets, you can combine both techniques: partition the data first by a broad, low-cardinality category (like order_date) and then bucket each partition by a granular, high-cardinality identifier (like customer_id). 

For bucketing
Formula: k = 1 + log_2(n) Example: For 100 records, k = 1 + 6.64 = 7.64 → 8 buckets.

F) Repartition vs coalesce.
In Apache Spark,  is used only to decrease the number of partitions efficiently by merging existing ones without a full shuffle, whereas  can both increase or decrease partition counts by performing a full data shuffle to ensure an even distribution.
Key Differences 

• Shuffle Operation: 

	• : Avoids a full shuffle (narrow transformation) by combining local partitions. 
	• : Always triggers a full network shuffle (wide transformation). 

• Direction: 

	• : Can only decrease the partition count (unless shuffle is explicitly set to true). 
	• : Can increase or decrease the partition count freely. 

• Data Distribution: 

	• : May result in uneven or skewed partition sizes because data is not completely re-indexed. 
	• : Guarantees a uniform, evenly balanced distribution of data across all partitions. 

• Performance: 

	• : Faster and uses fewer resources when scaling down. 
	• : Slower due to high network I/O and disk write overhead from shuffling. 

When to Use Which 
Use  when: 

• You have filtered a large dataset and want to reduce the high number of output partitions before writing data to disk (e.g., to prevent creating thousands of tiny files). 
• You want to speed up execution time by avoiding expensive network shuffling. 

Use  when: 

• You need to increase the number of partitions to increase parallelism. 
• You are dealing with severe data skew and need to evenly balance records across partitions before a join or aggregation.
